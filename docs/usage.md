# 使用与配置

[返回项目首页](../README.md)

本文补充当前源码的设置、检测、台标和本地运行细节。已发布版本的差异请查看[发行说明](https://github.com/Ringas/iptv-studio/releases)。

## 台标订阅与优化

在「源管理 → 添加订阅」选择「台标 · JSON」，填写下载地址，保存后自动更新当前订阅；卡片中的刷新图标可单独重试，顶部「更新订阅」更新所有已启用订阅。直播、节目单和台标均可沿用默认更新计划，或单独设置更新间隔。关闭定时更新或停用订阅后，仍可手动刷新或保存触发更新，订阅启停保持不变；手动更新和保存更新不触发线路检测。同类型修改地址时，获取失败保留旧快照。

检测或更新任务运行时，仍可新增、编辑、停用或删除订阅。订阅信息立即保存，内容更新排队执行；同一订阅只更新最后保存的版本，队列在重启后保留。停用或删除会取消该源待更新项；旧更新和旧检测结果不再覆盖已变更的源及启停状态。手动保存、单源刷新不触发线路检测。

台标 JSON 支持名称映射：

```json
{"CCTV1":"https://example.com/CCTV1.png","江苏卫视":"https://example.com/江苏卫视.png"}
```

也支持 `[{"name":"CCTV1","id":"可选节目单ID","url":"https://example.com/CCTV1.png"}]`。图片可为 PNG、JPEG、WebP，支持相对地址；台标订阅不增加直播频道。多个台标订阅按资料优先级、添加顺序匹配，频道别名沿用直播订阅的名称归一规则。

匹配顺序：手动台标 → 台标订阅 → 直播源自带台标 → 节目单台标。台标条目缺失或图片加载失败时尝试后续候选；更新失败保留旧快照，停用或删除台标订阅后恢复源台标。

「设置与订阅 → 台标 → 台标优化」提供关闭、浅色、深色、透明。默认关闭，保留原图样式。保存设置即生效，并独立进入台标处理队列，不依赖下一轮订阅更新或线路检测；检测运行时批量队列让出资源。开启后按透明边界等比例调整图案占比，统一为 300×180 的背景与留白，浅色模式对明确白底保守去底，再将透明图案叠加浅色背景，不添加描边；CCTV、CGTN 等近白图案保留原浅色对比描边。深色模式保留现有细描边，透明模式保留透明通道，不添加背景或描边。图片内已有的实色底板不会强行抠除。频道卡片、线路列表、频道详情及 M3U/JSON/XMLTV 导出共用处理结果。

图片缓存在数据目录的 `logo-cache`，按解码后的图案内容去重，不按图片地址保存多份。不同地址首次需要读取图片确认内容，相同图片共用原图和各模式结果。每 7 天核验正在使用的台标来源；内容未变只更新检查时间，不重做优化、不覆盖已有图片；变化后生成新结果，并清理失去引用的旧内容。共享台标只在最后一个引用移除后清理。周检独立于订阅更新间隔，线路检测期间等待；检查失败继续使用旧图，1 小时后重试。前后台并发请求合并处理；旧缓存升级时优先继续显示，并在后台补齐内容索引。缓存不进入发布包或镜像；复用已有 FFmpeg，不增加 Pillow 等运行依赖。播放器需能访问本服务的台标地址，建议为跨网络订阅配置 `PUBLIC_BASE_URL`。

台标优化进度独立于线路任务：后台批量处理在线路检测期间等待，检测结束后继续；前台任务区域优先显示线路进度，并附台标等待提示。运行日志输出台标开始、阶段进度、等待/恢复及完成汇总，不写入前台历史任务记录。缓存命中计为已就绪，相同台标去重，无台标频道跳过。已开始的单张处理和用户主动查看未缓存台标仍可能短暂占用资源。

## 检测与启停

### 三种检测方式

| 方式 | 适用情况 | 验证取舍 |
| --- | --- | --- |
| 快速检测 | 大批量初筛、快速了解线路状态 | 验证窗口较短，结果不能等同于长时间稳定性验证 |
| 均衡检测 | 日常更新和多线路比较 | 粗筛接续连续精测，复用下载与解码证据；受控双线路调度，同网关串行，不达标线路隔离复核 |
| 深度检测 | 重点线路复核 | 连续观察解码和直播推进，以更多时间换取更充分的证据 |

三种方式使用同一组通过门槛，但采样时长与证据充分程度不同。连续精测检查多帧解码、时间戳与直播推进；不是只看 HTTP 200 或清单标注的分辨率。

新建配置默认使用**快速检测**，同时要求实测速率 **严格大于 100 KB/s**、画面高度 **至少 720 像素**。KB/s 是每秒字节速率，不是 kbps。设置可改为仅速率达标、仅分辨率达标，或调整数值门槛；已有用户设置保留，不会因升级强制改回默认值。

### 结果、当前达标与启停分别表示什么

- **当次检测结果**：该次采样的证据、时间和当时门槛，作为历史记录保留。
- **当前是否达标**：读取已保存的检测结论。保存通过条件不重算已有结果，后续检测统一使用新设置。
- **线路启停**：决定是否进入播放器订阅。手动操作立即生效，不要求先达到自动检测门槛。

429 限流、网络策略拦截和临时超时保留为未能验证，不能直接认定废源；可按规则冷却、隔离复核。检测全部线路包含可见的未测、不达标和手动停用线路，隐藏线路及停用订阅不在此范围内。

### 自动检测与手动操作

新建配置默认开启更新计划，间隔 **8 小时**，并开启更新后检测、按检测结果自动启停。订阅可单独设置更新间隔。

开启「按检测结果自动启停」时，以下四个入口使用一致规则：更新计划中的更新后检测、检测全部线路、检测所选线路、检测此线路。

- 某线路的**首测取得有效达标或不达标结果**后，清除该线路的手动覆盖，恢复按结果自动启停。
- 未检测到的线路，以及限流、超时等未能验证的结果，保持原启停状态。
- **同一次任务内的异常复测**只更新检测记录与提示，不再次改变启停状态。
- 关闭自动启停后，检测不会覆盖手动启停。

没有“恢复自动”按钮；对线路再次发起检测并取得有效首测结果即可。单纯更新订阅、打开试播或切换播放线路不等于自动检测。

## 首选线路与订阅一致性

已启用线路优先。对于同样达标、流畅且无失败的线路，优先比较画质和速率，不因成功检测次数较多而优先；失败、重连和卡顿仍会降权。

首选播放与订阅导出始终使用最新的启停状态和质量排序；保留多线时按此顺序输出，仅发布最佳线路时输出首条已启用线路。保存通过条件后，待线路重新检测才使用新规则。

当前源码中，界面展示顺序在本次浏览期间保持稳定，状态、指标与数量继续更新；重新进入页面、重新打开弹窗或手动刷新页面时再刷新展示顺序。该规则只影响界面排列，不改变首选播放和导出。线路仍使用“线路1、线路2……”编号；编号对应最新标准顺序，当前可视位置不代表首选优先级。

手动启用未达标线路仍可发布和播放，但不展示为达标速率；全部停用时不发布该频道，管理台仍可显式试播。卡片色点表示启停，不代表已通过检测。

## 本地运行

需要 **Python 3.10+、Node.js 22+、FFmpeg**。服务端使用 Python 标准库和 SQLite，不需要安装第三方 Python Web 框架或 npm 依赖。

```bash
git clone https://github.com/Ringas/iptv-studio.git
cd iptv-studio
DATA_DIR=./data BIND=127.0.0.1 PORT=8788 python3 app.py
```

打开 `http://127.0.0.1:8788`。Node 和 FFmpeg 应在 PATH 中；FFmpeg 可通过 `FFMPEG_BIN` 指定路径。局域网访问时将 `BIND` 改为本机局域网 IP，并使用该 IP 打开页面。

| 配置 | 作用 |
| --- | --- |
| `DATA_DIR` | 数据目录，保存 SQLite 数据库等持久内容 |
| `BIND` | 监听地址，本地调试建议用 `127.0.0.1` 或指定局域网 IP |
| `PORT` | HTTP 服务端口 |
| `TZ` | 运行时区，默认 `Asia/Shanghai`；仅需修改时设置 |
| `FFMPEG_BIN` | FFmpeg 可执行文件路径 |

已有本地环境可用 `start-local.command` 固定启动配置。它读取被 Git 忽略的 `.env.local`，其中需设置 `BIND`、`PORT`、`DATA_DIR`、`PYTHON_BIN`、`NODE_BIN`、`FFMPEG_BIN`。路径请填写本机实际绝对路径；该脚本要求原数据库已存在，避免误建空库。

```bash
./start-local.command --check  # 仅检查配置、依赖与原数据库
./start-local.command          # 启动原数据目录的服务
```

直接运行 `app.py` 不会读取 `.env.local`。端口已占用时应先正常停止原进程，不要启动第二个实例。

## 运行日志

后台默认输出简短中文日志，按进度、结果、策略和诊断等内容类型整行着色。时间统一为 `YYYY-MM-DD HH:mm:ss.SSS`，跟随服务端时区，默认上海，不显示 `+08:00`。默认不输出轮询与逐片细节。

排查持续故障可设置 `IPTV_LOG_LEVEL=DEBUG`，或用 `IPTV_LOG_FORMAT=json` 输出关联诊断。前台任务记录与后台诊断用途不同，详见[运行日志与排错](logging.md)。

## 常见问题

**为什么网页能打开，视频却不能播放？** 订阅可访问不代表媒体可访问。检查服务器到上游的网络、鉴权、限流及浏览器编解码支持；结合检测详情与独立播放器复核。

**为什么检测通过，长期播放仍可能卡顿？** 检测是有限时间的采样，不能保证后续网络与上游稳定，也不能由通过数量增加推断准确率提升。研究结论仅适用于记录中的样本和网络。

**订阅是否经过服务器转发媒体？** 导出的媒体地址通常由播放器直连上游；网页试播的会话代理与导出是不同路径。能取得订阅的人可能看到媒体地址，请在可信内网或 VPN 使用。公网部署需配置 HTTPS 反向代理，并在管理台设置访问密码。

**已有门槛为什么不是默认值？** 默认值仅用于新建配置，已有设置继续沿用。请在设置页调整并保存。


## 权限与播放器兼容性

管理台使用账号 `admin` 和配置的密码登录。管理接口鉴权不等同于播放器订阅鉴权：`/live.m3u`、`/live.txt`、`/live.json`、`/guide.xml` 在管理台鉴权之前处理，但仍经过网络访问检查；台标接口也不要求管理台登录。允许公网访问或配置反向代理时，应按实际需求在代理或 VPN 层保护这些路径。`PUBLIC_BASE_URL` 只改变输出地址的前缀，不提供访问控制。

网页试播使用 HTTP(S) 会话代理，不提供视频转码。M3U 中的 VLC/Kodi 参数会随 M3U 导出保留；网页试播只读取支持的请求头，不会执行任意播放器配置。请求头、编解码器、限流和鉴权差异都可能导致网页与外部播放器结果不同。

当前镜像发布和容器验证平台为 `linux/amd64`，不是已完成验证的多架构镜像。
